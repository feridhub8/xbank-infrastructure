# xbank-infrastructure

Docker setup of the infrastructure tools XBank uses. Nothing else lives here.

| Tool | Folder | Host port | Purpose |
|---|---|---|---|
| PostgreSQL | `postgres/` | 5432 | Database for Keycloak |
| Keycloak | `keycloak/` | 8180 | Identity provider, realms `xbank` (prod) and `xbankDev` (local, dev) |
| Vault | `vault/` | 8200 | Secrets store, KV v2 at `secret/` |

Ports can be changed in each tool's `.env`. If a locally installed PostgreSQL already uses 5432, set `POSTGRES_PORT` in `postgres/.env` to another port (for example 5433); Keycloak reaches PostgreSQL over the Docker network and is not affected.

## First setup on a machine

1. Create the shared network (required on every machine that runs XBank containers):

   ```bash
   docker network create xbank_network
   ```

2. Create the `.env` files from the examples and fill in every value (the examples list the keys only):

   ```bash
   cp postgres/.env.example postgres/.env
   cp keycloak/.env.example keycloak/.env
   cp vault/.env.example vault/.env
   ```

   `KC_DB_USERNAME`/`KC_DB_PASSWORD` in `keycloak/.env` must match `KEYCLOAK_DB_USER`/`KEYCLOAK_DB_PASSWORD` in `postgres/.env`. Ports left empty fall back to the defaults in the table above.

   PostgreSQL applies these credentials only when its volume is first created. To change them later, remove the `xbank_postgres-data` volume (this deletes the Keycloak database; realms are re-imported on the next start).

3. Start everything:

   ```bash
   docker compose up -d
   ```

4. Initialize Vault (once, see below) and copy the Keycloak client secrets into it.

## Start and stop

```bash
docker compose up -d
docker compose down
```

`docker compose down -v` also deletes all data volumes (database, Vault secrets). Do not use it unless you mean to start from scratch.

## Keycloak

- Admin console: http://localhost:8180, credentials from `keycloak/.env`.
- Realms are imported from `keycloak/realms/` on startup. Import skips realms that already exist, so after editing a realm JSON, delete that realm in the admin console and restart Keycloak:

  ```bash
  docker compose restart keycloak
  ```

- Every realm has the roles `USER` (given to every new user) and `ADMIN` (grant it by hand: Users > user > Role mapping).
- A user's username is their FIN, so Keycloak rejects a second user with the same FIN. Keycloak stores usernames in lowercase. Users log in with their email.
- Client `xbank-ms-auth` is confidential. Its secret is generated by Keycloak and is not in this repo: copy it from Clients > xbank-ms-auth > Credentials into Vault (see below).

## Vault

Vault keeps its data in a volume and starts **sealed** after every restart.

### First start (once)

```bash
docker compose exec vault vault operator init -key-shares=1 -key-threshold=1
```

Save the unseal key in your password manager. It is shown only once; without it the data cannot be recovered. Never commit it.

Then unseal and run the auth setup with the root token from `init`. The setup enables KV v2 at `secret/`, AppRole, and userpass; creates one AppRole per service and environment (for example `ms-auth-local`) that can read only `secret/xbank/<env>/<service>`; and creates the user `admin` with the password `VAULT_ADMIN_PASSWORD` from `vault/.env`:

```bash
docker compose exec vault vault operator unseal
docker compose exec -e VAULT_TOKEN=<root-token> vault /vault/setup/init-auth.sh
```

Check that `admin` can log in, then revoke the root token:

```bash
docker compose exec vault vault login -method=userpass username=admin
docker compose exec -e VAULT_TOKEN=<root-token> vault vault token revoke -self
```

The setup is safe to run again (as `admin` or root), for example after adding a service to `SERVICES` in `vault/setup/init-auth.sh`. Existing roles keep their role IDs.

### After every restart

```bash
docker compose exec vault vault operator unseal
docker compose exec vault vault login -method=userpass username=admin
```

### When a root token is needed

No root token is kept. Generate one from the unseal key, use it, and revoke it again:

```bash
docker compose exec vault vault operator generate-root -init
docker compose exec vault vault operator generate-root -nonce=<nonce>
docker compose exec vault vault operator generate-root -decode=<encoded-token> -otp=<otp>
```

### Service credentials

A service signs in with its AppRole `<service>-<env>`. Its role ID and a secret ID go into that service's own configuration (see the service's README):

```bash
docker compose exec vault vault read -field=role_id auth/approle/role/ms-auth-local/role-id
docker compose exec vault vault write -f -field=secret_id auth/approle/role/ms-auth-local/secret-id
```

### Secret layout

`secret/xbank/<env>/<service>`, where `<env>` is `local`, `dev`, or `prod`, and `<service>` is the repo name without `xbank-`. Example for the ms-auth client secret of realm `xbankDev`:

```bash
docker compose exec vault vault kv put secret/xbank/local/ms-auth keycloak-client-secret=<secret>
docker compose exec vault vault kv get secret/xbank/local/ms-auth
```

`local` and `dev` use the `xbankDev` realm's secret; `prod` uses the `xbank` realm's.

Web UI: http://localhost:8200

## Tests

The tests check the realm and Vault setup against the running infrastructure (start it first and unseal Vault). They run in a container on `xbank_network`, create only their own test users and secret IDs, and delete them at the end:

```bash
docker compose -f tests/docker-compose.yml run --rm --build tests
```

Each test prints `PASS` or `FAIL`; the command fails if any test fails.

Compose warns about "orphan containers" here because the tests share the `xbank` project with the tools. Ignore it, and never add `--remove-orphans`: it would remove the PostgreSQL, Keycloak, and Vault containers.
